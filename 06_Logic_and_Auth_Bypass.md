## 🟢 06_LOGIC_AND_AUTH_BYPASS / ПОДРЫВ ЛОГИКИ ПРИЛОЖЕНИЯ

Допустим, существует веб-приложение, которое реализует стандартную форму аутентификации по логину и паролю. 

Когда легитимный пользователь отправляет свой логин (`dolbaeb123`) и пароль (`ProMenia`), бэкенд проверяет эти данные, отправляя в БД следующий запрос:
```sql
SELECT * FROM users WHERE username = 'dolbaeb123' AND password = 'ProMenia'
Логика приложения:
Если база данных находит строку, где одновременно совпадают и логин, и пароль, она возвращает данные пользователя — вход выполнен успешно. В противном случае запрос возвращает пустоту, и авторизация отклоняется.

⚔️ EXPLOITATION STAGE / ОБХОД АВТОРИЗАЦИИ (AUTH BYPASS)
Поскольку приложение не фильтрует входящие параметры, атакующий может войти в систему под учетной записью любого пользователя (например, целевого юзера liquidgenius), вообще не зная его пароля.

Для этого в поле ввода username отправляется пейлоад: liquidgenius'--+, а поле password оставляется абсолютно пустым.

В результате SQL-запрос на стороне сервера трансформируется в:

SQL
SELECT * FROM users WHERE username = 'liquidgenius'--+' AND password = ''
Механика уязвимости:

liquidgenius' — Одинарная кавычка принудительно закрывает строковый литерал столбца username, ломая логику разработчика.

--+ — Комментарий SQL отсекает всю дальнейшую проверку. Для СУБД этот запрос физически превращается в укороченную версию:

SQL
SELECT * FROM users WHERE username = 'liquidgenius'
Результат: База данных обрабатывает только условие поиска по имени пользователя. Она находит в таблице юзера liquidgenius, возвращает его валидный профиль бэкенду, и приложение успешно авторизует атакующего в системе, полностью проигнорировав пустой пароль.
